# Backup and recovery

## What to back up
1. **PostgreSQL database** — all business data (the ledger, stock, documents, audit trail).
2. **Attachment storage** — `STORAGE_LOCAL_DIR` (or the object-storage bucket in production).
3. **Configuration** — your `.env` / secret store (never in git).

## In-app backup (Administration → Backup & reset)
Users holding `admin.backup` (Owner by default) can download a full backup at any time: a gzip-compressed SQL script of `INSERT` statements for every table, in foreign-key order. It is generated by the API (`GET /api/v1/admin/backup`), so it works on hosts without shell access (e.g. Laravel Cloud).

- **Contains** all business data: catalogue, stock and cost pools, sales, purchases, payments, journals, customers, suppliers, users (with password hashes), roles, settings and the audit log. **Not included:** live login sessions, the generated signing secret, idempotency records and the migration log — after a restore everybody signs in again.
- **Keep it private** (personal data and password hashes).
- **Restore** (technician):
  1. Create a new, empty PostgreSQL database.
  2. Point `DATABASE_URL` at it and run `pnpm db:migrate` with the **same application version** that produced the backup (the header line *Schema version* names the last migration).
  3. `gunzip backup.sql.gz` then `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f backup.sql`.
  4. Start the application on that database.
- The script runs in one transaction and refuses to run on a database that already holds a business. It needs no superuser rights: links that point "forward" (sub-accounts, journal reversals, serial numbers sold) are filled in by `UPDATE`s at the end, and closed fiscal periods are closed again last, so the append-only and period-lock triggers stay active.
- Verified in development: a demo database restored into a fresh database matched table-for-table (row counts), with balanced journals; an automated test covers voided sales, reversed journals and closed periods.

## Clearing the application (Administration → Backup & reset)
Users holding `admin.reset` (Owner by default) can clear the application after typing the business name and their password:
- **Transactions only** — sales, returns, payments, purchases and receipts, supplier invoices and payments, stock movements and balances, counts, transfers, adjustments, expenses, cashier sessions, journals, approvals, notifications and queues. Products, customers, suppliers, users, branches, registers, chart of accounts, financial accounts, tax rates, units, settings and the audit log stay; stock becomes zero and document numbers restart.
- **Everything** — the above plus products, variants, barcodes, price lists, categories, brands, departments, customers, customer groups and suppliers.
The tables are emptied with `TRUNCATE` in a single statement (the append-only triggers stay in force for normal operation), and an `application.cleared` audit event is recorded. It is refused when the database holds more than one business. **Download a backup first: clearing cannot be undone.**

## Database backups
Daily logical backup (keep at least 30 daily + 12 monthly copies, encrypted, off-site):
```bash
pg_dump --format=custom --no-owner --file="retail-$(date +%F).dump" "$DATABASE_URL"
```
For lower data-loss windows use managed PostgreSQL with point-in-time recovery (WAL archiving), e.g. 7–35 days PITR.

## Restore
```bash
createdb retail_restore
pg_restore --no-owner --dbname=postgresql://…/retail_restore retail-2026-11-11.dump
DATABASE_URL=postgresql://…/retail_restore pnpm db:check     # schema matches the code
DATABASE_URL=postgresql://…/retail_restore pnpm db:migrate   # apply any newer migrations
```
Then run **Accounting → Reconciliation** (or `GET /api/v1/accounting/reconciliation`) and the trial balance to confirm integrity before switching traffic.

## Restore drills
Test a restore into a scratch database at least monthly and record: backup age, restore duration, reconciliation results.

## Notes
- Journal and stock tables are append-only by trigger; do not "fix" data with manual SQL — post reversals/adjustments through the application so the audit trail stays intact.
- Restoring an older backup loses transactions after that point; reconcile tills and payment-provider statements for the gap.
